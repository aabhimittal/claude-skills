# commit-lint rule catalog

Stable rule IDs and severities. `critical` > `high` > `medium` > `low` > `info`.
Default CI gate (`--fail-on`) is `high`, so only genuinely malformed headers
break a build — style nits are advisory.

| Rule | Severity | Trigger | Fix |
| --- | --- | --- | --- |
| CL001 | high | Empty commit message | Write `type(scope): summary` |
| CL002 | high | Header doesn't match `type(scope)!: subject` | Add the type prefix, colon, and single space |
| CL003 | medium | Type is not lowercase (`Feat:`) | Lowercase it |
| CL004 | medium | Unknown type | Use an allowed type, or extend with `--types` |
| CL010 | medium | No blank line between header and body | Insert an empty line after the header |
| CL005 | low | Empty scope parentheses `feat():` | Name the scope or drop the parens |
| CL006 | low | Subject starts with a capital (acronyms exempt) | Lowercase the first word |
| CL007 | low | Subject ends with a period | Drop it — the subject is a title |
| CL008 | low | Non-imperative subject ("added", "fixes") | Use the imperative: "add", "fix" |
| CL009 | low | Header longer than 72 characters | Tighten; move detail to the body |
| CL011 | low | Body line longer than 100 characters | Wrap the body (URLs/tables exempt) |
| CL012 | low | `BREAKING CHANGE:` footer without `!` in the header | Add `!` before the colon |

**Exempt by design:** `Merge …`, `Revert "…"`, and `fixup!`/`squash!`/`amend!`
commits are skipped — they're generated by git and shouldn't be rewritten.

## The format

```
type(scope)!: subject

body explaining what and why (not how)

BREAKING CHANGE: what broke and how to migrate
Refs: #123
```

- **type** — `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`,
  `chore`, `style`, `revert` by default. Override with
  `--types feat,fix,docs,custom`.
- **scope** — optional area of the codebase (`api`, `ui`, `deps`).
- **`!`** — marks a breaking change; pair it with a `BREAKING CHANGE:` footer
  describing the migration.
- **subject** — imperative, lowercase, no trailing period. It should complete the
  sentence "this commit will …".

## Why the imperative mood (CL008)

Git's own generated messages use it ("Merge branch…", "Revert…"), and the header
reads as an instruction to the codebase. "add pagination" describes what applying
the commit *does*; "added pagination" describes history and reads inconsistently
in a `git log` where every other line is imperative.

## Changelog generation

`changelog` mode groups the same parsed commits into a Keep-a-Changelog-style
release note:

- **⚠ BREAKING CHANGES first**, using the `BREAKING CHANGE:` footer text when
  present (falling back to the subject).
- Then one section per type in a stable order (Features, Bug Fixes, Performance,
  Refactoring, Documentation, Tests, Build System, CI, Styling, Reverts, Chores).
- Scopes are bolded (`**api:** add pagination`) and each entry carries its short
  sha.
- Non-conventional commits land under **Other** rather than being dropped, so
  nothing silently disappears from a release note.
- Merge/revert/fixup commits are excluded.

## Notes & limitations

- CL008's non-imperative detection is a word list of common past-tense and
  gerund openers, so an unusual verb may slip through. It never guesses at
  meaning — it only matches known forms, which keeps false positives near zero.
- CL006 deliberately allows leading acronyms (`feat: API rate limiting`).
- Body-length checks skip lines that look like URLs, emails, or table rows, since
  those can't be wrapped.
- `--range` shells out to read-only `git log`; it never modifies history.
